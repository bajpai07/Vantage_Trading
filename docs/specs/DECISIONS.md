# VANTAGE — DECISIONS.md

Format: ID · Decision · Why · Alternatives · Trade-off/risk · Status. Revisit rule: a decision changes only via a new entry that supersedes it (never silent edits).

| ID | Decision | Why | Alternatives | Trade-off / risk |
|---|---|---|---|---|
| D-01 | **Modular monolith**, one repo, 4 processes (api, execution-worker, market-data-worker, jobs-worker) | Fits 1–3 engineers; process isolation without distributed-systems cost | Microservices; single process | Needs discipline: boundary lint, no cross-module table access. Extraction triggers listed in ARCHITECTURE §10 |
| D-02 | **PostgreSQL as the only source of truth** for money; Redis for ephemeral quotes/fanout/queues | ACID, constraints, row locks, mature | Event store + projections; NoSQL | Hot-account lock contention (mitigated by serial per-account processing) |
| D-03 | **Double-entry, append-only ledger with DB-level triggers** (balance per currency at commit; non-negative cash via CHECK) | Defence in depth: bugs in code cannot silently corrupt books | App-only checks; single-entry balance column | More SQL to maintain (hand-written migrations), slightly slower writes |
| D-04 | **USD base account; cash held in USD only**; INR purchases convert USD→INR inside the trade via FX_CLEARING with the rate id stored | One buying-power number; simple UX; correct FX P&L | Multi-currency wallets now; INR-based accounts | Users cannot "hold INR cash". Wallets are a P3 option needing no schema change |
| D-05 | **US equities launch on licensed DELAYED data** (≈15 min), labelled; REAL_TIME is an upgrade | Cost and licensing simplicity; honest labelling | Free IEX-only real-time (not consolidated; terms unclear for redistribution); full SIP at launch | Less "live" feel; mitigated by crypto being real-time and clear UX copy |
| D-06 | **Crypto from one USD-pair exchange feed with written display terms + a commercial aggregator as fallback**; USD-quoted pairs only | Avoids stablecoin FX assumption; clear terms; 24/7 | Binance USDT pairs; aggregator only | Venue terms/regional restrictions need verification; fewer pairs |
| D-07 | **NSE/BSE only via an authorised vendor under written licence**; broker APIs and scraping forbidden for users | Redistribution rights | Broker API quick start; scraping | Cost and lead time; INR markets gated behind `tradable_in` until licensed |
| D-08 | **Execution model QBX-1: quote-based, deterministic, no order book, no partial fills in MVP**, slippage = base + size term | Honest, testable, implementable on quote data | Simulated order book; random slippage | Less realistic for large orders/illiquid names; limitations displayed |
| D-09 | **Execution on DELAYED data allowed** per asset-class flag, always labelled and stored with `entitlement`; STALE/CLOSED/UNAVAILABLE block | Without it a delayed-data launch cannot trade; "what you see is what you fill" | Block all delayed execution; fill at "estimated live" price (fabrication) | Competitions need equal-entitlement rules (PRD §5.11) |
| D-10 | **Long-only cash account** (no shorting, margin, leverage) in MVP and P2 | Removes liabilities/margin calls from the accounting model | Margin simulation | Narrower strategy range; revisit with a separate spec |
| D-11 | **FIFO lot accounting**; average cost is derived display | Deterministic, tax-style familiar, enables exact P&L and FX P&L per lot | Average cost; specific-lot | FIFO only; no user choice |
| D-12 | **Fees expensed separately** (FEES account), not capitalised into lot cost; net P&L = gross − fees | Clear reporting; simple ledger recipes | Capitalise buy fees | Slightly different from some tax treatments; not tax software |
| D-13 | **Collar-based reservation**: BUY reserves `qty×ref×(1+collar)×fxbuf+fee`; fill beyond reserve → `PRICE_MOVED` reject | Guarantees no overspend without margin; deterministic | Allow negative cash; re-reserve at fill | Occasional rejects in fast markets (collars tunable) |
| D-14 | **Crypto quantities live in lots/positions; ledger holds only USD cost** | Keeps ledger balanced in fiat currencies; avoids crypto-as-currency complexity | Crypto ledger accounts per asset | Needs migration if crypto-for-crypto or wallets are added (P3), designed as additive |
| D-15 | **Prisma for CRUD, raw SQL for ledger/locking/triggers; hand-written SQL migrations alongside** | Productivity where safe, control where it matters | Drizzle/Kysely everywhere; TypeORM | Two access styles; schema-drift CI check required |
| D-16 | **NestJS** | Module system maps to bounded contexts; DI for testability | Fastify + own structure; Go | Heavier; engine kept framework-free so it can be extracted/ported |
| D-17 | **Hosting: managed containers + managed Postgres/Redis in one region; closed beta may use one VM with Compose** | Low ops burden; PITR/backups from the provider | Kubernetes; serverless | Provider lock-in is modest; region choice per first cohort |
| D-18 | **Single write region**; region chosen after first cohort (India-heavy → Mumbai, US-heavy → US-East) | Simplicity; avoids multi-master | Multi-region active-active | Cross-ocean latency for some users; acceptable for simulation |
| D-19 | **Opaque server-side sessions (cookies) with Argon2id** | Revocation, no token theft via JS | JWT access tokens | Needs session store lookups (cheap with Redis cache) |
| D-20 | **WebSocket gateway inside the api process initially, with `account_events` outbox + per-account `seq`** | Fewer moving parts; reliable replay | Separate gateway now; SSE | Extract at ~5k connections/node |
| D-21 | **Stop trigger uses last (fallback mid); gap-through fills at gap price** | Realistic, deterministic | Trigger on bid/ask | Illiquid names have noisy last; configurable per class |
| D-22 | **Age 18+ only; store `is_adult` + country, not date of birth** | Minimise PII and regulatory exposure | Collect DOB; allow minors with guardian | Verify with counsel before launch |
| D-23 | **FX for INR: vendor bid/ask where licensed, else reference mid ± disclosed modelled spread (labelled)** | Honest label; works without a pricey FX feed | Mid only; hard-coded rate (rejected) | Modelled spread is not a tradable quote; disclosed |
| D-24 | **No raw ticks in Postgres; candles with retention tiers; quote snapshots 30 d** | Cost and performance | Store all ticks | Cannot replay tick-level history beyond recorded test files |
| D-25 | **AI coach is read-only, tool-fed, numbers rendered from tool results** | Prevents fabricated prices; no trading authority | Free-form LLM answers | More engineering; safer |
| D-26 | **Feature gating by `instruments.tradable_in` and `provider_feeds` config with licence refs** | Phased market launch without code forks | Separate branches | Config must be audited (CI test) |
| D-27 | **Nightly reconciliation freezes accounts on violation** | Prevents compounding corruption | Alert only | A bug could freeze many accounts; alert-first thresholds and an admin unfreeze flow |
| D-28 | **Mobile = responsive web (reorganised panels) in MVP; PWA in P2** | Solo capacity | Native apps | Less native polish |
| D-29 | **One-process modular monolith first** | Smallest moving parts for a solo build; module boundaries keep later extraction possible | Four processes from day one | Needs boundary discipline. Status: APPROVED by founder (M0) |
| D-30 | **Synchronous market-order execution**: one atomic transaction, account-level locking, idempotency and full validation (mandatory) | Simple, correct and testable; no half-filled states for market orders | Queue plus execution worker from day one | Hot-account contention bounded by account-level locking. Status: APPROVED by founder (M0) |
| D-31 | **Multi-currency schema, but USD-only balances and trading in the first MVP** | Avoids a schema change when INR arrives (see D-04) | USD-only schema | Extra columns unused at first. Status: APPROVED by founder (M0) |
| D-32 | **ETFs use the same pipeline as stocks** | No special cases; same instrument model | Separate ETF handling | ETF-specific data gaps are handled later. Status: APPROVED by founder (M0) |
| D-33 | **Whole shares in the MVP** (TRADING_ENGINE §1: fractional off, flag-controlled later; the instrument has `fractional_ok`) | Simpler rounding and lot logic | Fractional shares at launch | Less flexible position sizing. Status: APPROVED by founder (M0) |
| D-34 | **Stack unchanged**: NestJS, Prisma for non-ledger tables, raw SQL for the ledger, Next.js (see D-15, D-16) | Already decided; M0 adds none of it | Revisit the stack now | None new. Status: APPROVED by founder (M0) |
| D-35 | **Plain-SQL forward-only migrations via node-pg-migrate** | Full control for triggers and constraints; one wrapper, observed behaviour in docs/migrations.md | Prisma Migrate only | Hand-written SQL to maintain. Status: APPROVED by founder (M0) |
| D-36 | **Two env files; apps never get migration credentials** | Limits the blast radius of an application compromise | One shared env file | Two files to manage. Status: APPROVED by founder (M0) |
| D-37 | **Layout deferral**: `engine`, `market-model`, `contracts`, other apps and `apps/web` are created when needed, not in M0 | Avoids empty speculative packages | Create the full layout up front | Imports must be added when packages appear. Status: APPROVED by founder (M0) |
| D-15 (note) | **Superseded by D-35** (plain SQL migrations via node-pg-migrate; Prisma is a client for non-ledger tables only, schema by introspection, no `prisma migrate`) | Added in M1; D-15 text above is unchanged | | Status: APPROVED by founder (M1) |
| D-38 | **`accounts.user_id` foreign key is added in M2** (the column is `uuid NOT NULL` now, without a reference to `users`; the unique partial index `accounts_one_main` stays) | `users` does not exist in M1; the M2 migration that creates it adds the constraint | Create a placeholder users table in M1 | Until M2 an account can point at a user id that does not exist. Status: APPROVED by founder (M1) |
| D-39 | **MVP recipes post fills directly, with no RESERVED movement**, because execution is synchronous (D-30); the `RESERVED` ledger account type stays in the schema for later | Fewer postings and no reservation state to reconcile | Reserve then fill (TRADING_ENGINE section 5.1 reserve flow) | Reservation recipes must be added if asynchronous execution is ever introduced. Status: APPROVED by founder (M1) |
| D-40 | **Ledger layering**: pure recipes in `packages/engine`, SQL in the `apps/api` ledger module; `apply_entry` is SECURITY DEFINER; the app role has no UPDATE, DELETE or TRUNCATE; the entry currency must match its ledger account (guard added to `apply_entry`) | Balances move only through entries; the engine stays testable without a database | App role with UPDATE on `ledger_accounts` | SECURITY DEFINER code must keep its fixed `search_path` and revoked PUBLIC execute. Status: APPROVED by founder (M1) |
| D-41 | **All new IDs are UUIDv7**, generated in `apps/api` through one `newId()` function (pinned `uuid` package); `money` and `engine` never generate IDs; M1 code is left as it is | Index locality (DATABASE section 1) with one place to change | Keep `randomUUID()` (v4) | Two id generators coexist until M1 code is migrated. Status: APPROVED by founder (M2) |
| D-42 | **Email verification is deferred to the closed-beta hardening phase (M8)**: new users are `ACTIVE` with `email_verified_at = NULL` (deviates from the DATABASE default `PENDING_VERIFICATION`); trading and balance endpoints require `ACTIVE` | Lets M2 deliver the full register, login and balance flow without an email system | Verification in M2 (needs email sending) | Anyone can register with an email they do not own; abuse is limited by rate limits only. Status: APPROVED by founder (M2) |
| D-43 | **Prisma is not introduced in M2**: registration creates the user, account, ledger accounts and GRANT in one `pg` transaction, which Prisma cannot join with the ledger repository. Prisma arrives with the first non-ledger CRUD table (watchlists, M3). Ledger and registration always use `pg` | One transaction across identity and ledger | Prisma for users now | Two data-access styles later. Status: APPROVED by founder (M2) |
| D-44 | **Ledger hardening from the M1 review**: (a) an entry currency must equal its ledger account currency (added to `apply_entry` in M1); (b) a ledger transaction must have at least one entry at commit (deferred constraint trigger, migration 0007) | Closes two gaps found after M1: a USD entry moving an INR balance, and empty transactions | Leave both to application code | Raw SQL that inserts a transaction row must add its entries in the same transaction. Status: APPROVED by founder (M2) |
| D-45 | **Watchlists and instrument reads use plain `pg` repositories** (like the ledger); Prisma is deferred again | The CRUD surface is tiny, and a second database client adds generate/introspection steps on Windows and in CI for little value | Introduce Prisma with watchlists (D-43 plan) | Re-evaluate when CRUD volume grows (M5/M6). Status: APPROVED by founder (M3a) |
| D-46 | **Quote store is an in-memory `QuoteStore` behind an interface** (single process) | Nothing else needs Redis yet; the interface is async so a Redis store drops in | Redis now | State is lost on restart (quotes read UNAVAILABLE until the next snapshot) and cannot be shared by several processes. Status: APPROVED by founder (M3a) |
| D-47 | **The calendar source of truth is `exchanges.calendar` (JSONB)**, filled by a SQL migration from the exchange's official published calendar and validated with Zod at load; a yearly update is a new forward-only migration | Auditable, versioned with the schema, no runtime dependency on a vendor | A holiday library or a vendor calendar endpoint | Must be refreshed every year or the market shows as closed past `coverage.to`. Status: APPROVED by founder (M3a) |
| D-48 | **A `FixtureProvider` exists for local/test only**; its instruments carry `attrs.source = 'FIXTURE'`; startup refuses to boot in staging or production when any instrument has `attrs.source = 'FIXTURE'` or the quote source is FIXTURE | Makes it impossible for synthetic prices to be shown as real | Rely on configuration alone | The guard needs the database, so it runs at application bootstrap. Status: APPROVED by founder (M3a) |
