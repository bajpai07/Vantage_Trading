## 1. Goal
Add **resting LIMIT orders** for stocks and crypto, fully inside the existing financial guarantees:
- a limit BUY **reserves cash** (ORDER_RESERVE) and a limit SELL **reserves quantity** (`positions.qty_reserved`);
- the order rests as `ACCEPTED`, is filled by a **matcher** when the simulated quote crosses the limit, or is **cancelled** by the user, or **expires**;
- every path posts exact double-entry ledger transactions, and the reconcile invariants I3, I4, I5, I6, I7, I10 (TRADING_ENGINE §11) hold with **zero tolerance** after every step.

This is the first time orders change state after insert and money is held back. It is the second riskiest change after M8. The M4a–M8 behaviour of MARKET orders must not change except where stated.

**Out of scope (do not build):** STOP and STOP_LIMIT orders, partial fills, IOC/FOK, order modify/replace, brackets/OCO, the simulated order book / depth display (M8b-2), UI redesign (M9), live exchange adapter, INR, wallets.

## 3. Decisions (record as the next free D numbers, starting at D-91, in this order, `APPROVED by founder (M8b-1)`; object with a reason if one is wrong)
- **D-91 Order lifecycle revisits D-49 (orders were inserted once, in final state).** MARKET orders keep the M4a behaviour (inserted FILLED or REJECTED, never updated). LIMIT orders are inserted `ACCEPTED` (or `REJECTED`) and later change by **guarded transitions only**: `UPDATE orders SET status=$new, version=version+1, … WHERE id=$id AND version=$v AND status='ACCEPTED'`; zero rows updated = lost race (cancel → `ORDER_NOT_OPEN`, matcher → skip). Allowed: `ACCEPTED→FILLED`, `ACCEPTED→CANCELLED`, `ACCEPTED→EXPIRED`. Terminal states have no outgoing transitions. A DB trigger enforces this for `vantage_app`: only `status, filled_qty, reserved_usd, version, updated_at` (and `triggered_at` if present) may change, only along the allowed edges, `version` must increase by exactly 1, identity columns (`account_id, instrument_id, side, type, tif, qty, limit_price, client_order_id, created_at`) never change, and terminal rows never change at all. `order_events` is append-only with contiguous `seq` per order (inspect what M4a built and extend, do not duplicate). Because there are no partial fills, `filled_qty` goes 0 → `qty` in one step and the I5 deferred trigger (filled_qty = Σ executions.qty) is checked at commit.
- **D-92 Limit BUY reserve.** TRADING_ENGINE §6 gives `R = ceil8(qty × ref_price × (1 + collar) + est_fee)` and also says a limit buy "uses limit as ref_price, so its reserve is exact and cannot be exceeded". These conflict on the collar. Decision: for LIMIT BUY the fill price is never worse than the limit, so **no collar is applied**: `R = ceil8(qty × limit + commission(qty × limit))`, where `commission` is the same function used at fill (8 dp HALF_EVEN) on the maximum notional. Commission must be monotone non-decreasing in notional (assert with a property test) so the actual `C + f ≤ R` always; if it ever failed the fill must be refused and the order left intact (never overspend). Record as a clarification of §6, existing text untouched.
- **D-93 Supported scope.** Types: MARKET (unchanged) and LIMIT. TIF: `DAY` and `GTC` only (IOC/FOK, stop types and modify are rejected as a 400 validation error with a clear message). Cancel is **synchronous** `ACCEPTED→CANCELLED` (the `CANCEL_REQUESTED` state is not used in MVP; amendment note on §7). No partial fills (MVP per §4).
- **D-94 Expiry.** `expires_at` is set at accept. GTC: now + `GTC_EXPIRY_DAYS` (config, default 90). DAY for stocks/ETFs: the next NYSE session close after accept (use the calendar already built; if accepted while closed, the close of the next session). DAY for crypto: the next 00:00 UTC (crypto has no session; state this as an illustrative rule). Expiry runs as a periodic job **and** lazily (an order past `expires_at` is expired inside the same transaction before it can be matched or cancelled). EXPIRED posts ORDER_RELEASE exactly like cancel.
- **D-95 Matcher.** An in-process worker (config `MATCHER=on|off`, default off in tests unless started explicitly, on in dev) wakes every `MATCHER_INTERVAL_MS` (default 1000). For each instrument with open orders it takes the **current eligible quote** from the same provider/validation the order pipeline uses; STALE, CLOSED, UNAVAILABLE quotes are **not evaluated** (§3) and when a quote returns it is evaluated against the new quote only (no back-filling). Open orders for an instrument are evaluated in `created_at, id` order, at most one fill per order per quote event. Eligibility: BUY when `ask ≤ limit`; SELL when `bid ≥ limit`. Fill price: BUY `min(limit, slippage-adjusted ask)`, SELL `max(limit, slippage-adjusted bid)` (slippage-adjusted values rounded to tick exactly as for market orders: buy up, sell down); never worse than the limit. Fill idempotency key `fill:{orderId}:1`; a replay hits the unique constraint and is treated as already done. Single active matcher: take a Postgres advisory lock per tick (try-lock; if not acquired, skip) so two API processes never double-process; correctness must still hold without it (row locks + guarded transitions are the real protection). The matcher must be a plain function `runMatcherOnce(deps, now)` that tests call directly with an injected quote source and clock; the timer is a thin wrapper.
- **D-96 Sells and `qty_reserved`.** A SELL (market or limit) may only use `positions.qty − positions.qty_reserved`. This changes the existing market-SELL availability check and `maxQty` for SELL (available, not total). Reserved quantity is released on cancel/expire/fill exactly. FIFO lot consumption at fill is unchanged (M8 rule, `cost_remaining`); the lots are not marked reserved, only the position's `qty_reserved` counter.
- **D-97 Marketable limit at accept.** If the order is marketable on the current eligible quote when accepted, it is reserved and filled **in the same transaction** (the order is never visible as resting). The ledger shows ORDER_RESERVE then FILL, the reserve is released through the FILL recipe (`CASH +(R − C − f)`). A limit that is not marketable rests. A limit order on a STALE/CLOSED/UNAVAILABLE quote is **accepted and rests** (it is just not evaluated), except that MARKET_CLOSED stocks follow the same rule; the ticket must say "will be evaluated when the market is open and the quote is live". Reject codes for limits: the existing ones plus `TICK_VIOLATION` (limit price not a multiple of the instrument tick) and `INSUFFICIENT_BUYING_POWER` / `INSUFFICIENT_POSITION` computed against **free** cash (`CASH`, reservations already removed) and free quantity (D-96).

## 5. Common mistakes
Locking in a different order than M4a (deadlocks); updating an order without the guarded `WHERE version/status`; letting the matcher read a quote outside the shared validation (stale fills); forgetting `qty_reserved` in the market SELL check; releasing the reserve by recomputing instead of using the stored `reserved_usd`; a different fee/price formula in preview, accept, matcher; float or `parseFloat` anywhere; rounding the fee on the reserve differently from the fill; leaving RESERVED non-zero after a terminal state; swallowing errors in the matcher loop; a timer that overlaps itself; weakening a test to get green; editing applied migrations; adding STOP/IOC "just in case".
