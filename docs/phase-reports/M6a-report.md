## 8. Deviations and spec questions

- **API addition (needs your confirmation):** the FIXTURE banner must show on the login page, and no existing public endpoint says which data source is active (`/v1/quotes` and `/v1/instruments` need a session). I added a read-only, unauthenticated `GET /v1/market/feed` (`{ source, entitlement, delaySeconds, enabled }`) with a contract, a test and a docs row. The prompt says to reuse existing code and keep `docs/api.md` to fixes; this is the only API change, recorded inside D-68.
- **API example port moved to 4000** (`.env.example` and the README line): the web app uses 3000 and `WEB_ORIGIN` stays `http://localhost:3000`, which is now the web app's origin because the browser reaches the API only through the proxy. The API's code default (3000) and its config tests are untouched; anyone with an old `.env` keeps working but must run the API and the web app on different ports.
- **Tailwind and the DESIGN_SYSTEM component list:** DESIGN_SYSTEM section 6 names shadcn/ui, Lucide, TanStack Table, Storybook and Lightweight Charts, and section 10 asks for Storybook stories, visual regression and a Lighthouse budget. The prompt asks for minimal dependencies, so only Tailwind (the spec says tokens live in its theme) was added; the rest comes with the screens that need it (D-64). I did not build the left rail with icons or the terminal grid (M6b); the nav is a top bar, and a bottom tab bar below 768 px.
- **A runtime proxy route instead of a Next rewrite** (D-65 allows "rewrite/proxy"): a rewrite bakes the API address into the build; the route handler reads it at request time, only passes `/v1/*` and `/health`, and is covered by tests.
- **Version choices:** Next 16.4.3, Tailwind 4.3.3 and Playwright 1.64.1 are one or more patch or minor versions behind the newest, because the newest were under two weeks old.
- **Rate limits and the proxy:** the API sees the proxy's address for every web user, so its per-IP login and registration limits are shared by all of them until a trusted-proxy setting exists (also noted in `docs/web.md` and D-65).
- **Footer and banner copy:** the prompt gives the exact banner text; the footer reads "Virtual money — not real trading. VANTAGE is a simulator, not a brokerage." (ARCHITECTURE section 8 asks for the "not a brokerage" disclosure).
- **No terms page exists**, so the registration checkbox says "I accept the terms and understand this is virtual money, not real trading" without a link.
- **Poll interval is configuration** (`PORTFOLIO_POLL_MS`, default 15000 as D-67 says) so the e2e run can use 2 seconds.

## 9. Known limitations and what M6b needs

Limitations:

- Tables scroll sideways inside their own region on small screens instead of turning into two-line cards; the page itself never scrolls sideways.
- The loading skeleton, the server-side load error screen and the private error boundary are untested (acceptance 10).
- E2E runs only in Chromium, only locally (not in CI), and uses a fixed injected clock; real-time behaviour, a non-FIXTURE data source in a browser, and Safari and Firefox are untested. No Lighthouse or bundle-size budget, no Storybook, no visual regression yet.
- The portfolio polls every 15 s while visible; a hidden tab stops and catches up (tested); there is no push.
- Dates and times are shown in UTC so server and browser always agree; a per-user time zone or locale setting does not exist (number format is fixed to commas and a dot).
- The email address is shown nowhere; only the display name is. Email verification and password reset arrive in M8.
- Equity history shows only what snapshots exist (daily, after the NYSE close; incomplete days are marked), so a new account sees "the equity curve appears once there are two daily snapshots".

What M6b needs (instrument search, instrument detail and the order ticket):

- **API endpoints it can already use:** `GET /v1/instruments/search?q=`, `GET /v1/instruments/:symbol`, `GET /v1/quotes?symbols=`, `GET /v1/market/status`, the watchlist endpoints (`GET/POST /v1/watchlists`, `PATCH/DELETE /v1/watchlists/:id`, `POST /v1/watchlists/:id/items`, `PUT .../items/order`, `DELETE .../items/:symbol`), `POST /v1/orders` (with the `Idempotency-Key` header), `GET /v1/orders/:id`, `GET /v1/positions`, plus the four portfolio reads used here. The proxy already forwards every `/v1/*` route, headers (including `Idempotency-Key`) and cookies; the client already validates responses and has `clientRequest` for POST.
- **Missing on the API side for a good ticket:** a pre-trade preview (estimated fill, fees, buying power after) is not an endpoint; the UI cannot compute it (no money arithmetic in the browser), so it needs a server preview or the ticket must show only what the quote says. Quotes need a refresh strategy (poll `/v1/quotes` visibly, with freshness labels), and `referencePrice` must be the bid or ask the user saw. A reject toast should reuse `reject-copy.ts`; the 429 and 401 paths and the idempotency-key reuse on retry already exist in `api-core` and `errors`.
- **UI work:** the terminal grid and left rail, a command/search box (`/`), keyboard shortcuts, the toast component, the order ticket with disabled states that always say why, and phone cards for the tables. Candles and charts (Lightweight Charts) need the daily and intraday candle data of M3b, which does not exist yet.
- **Before a public beta:** a trusted-proxy setting in the API so rate limits see real client addresses; CI for e2e; the Lighthouse and visual-regression gates from DESIGN_SYSTEM section 10.
