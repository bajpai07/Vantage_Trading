FOR UPDATE`, which `vantage_app` deliberately lacks on `accounts` and `ledger_accounts`. Solved with two narrow `SECURITY DEFINER` functions (see section 8) instead of granting UPDATE. 3. Three test-expectation mistakes found by the tests: result objects carry plain decimal strings (`'194.96'`), not database-formatted ones (`'194.9600000000'`), and a replay returned database formatting, so a replayed result differed from the first. Replayed values are now normalised the same way as fresh ones.
4. A comparison in the exactness test treated `SUM(qty_open x cost)` (scale 20) and the ledger balance (scale 10) as strings; it now compares exact decimals.

**Reference model used in the property test** (`trading-property.int.test.ts`, written independently of the engine and repository): all money in scaled integers (BigInt, 1 cent = 1,000,000 units of 1e-8), one array of lots per instrument with FIFO consumption by hand. BUY price = ceil(ask x 10002 / 10000) cents, SELL price = floor(bid x 9998 / 10000) cents; notional = qty x price; fee = round-half-even(notional x bps / 10000); `PRICE_MOVED` by integer cross-multiplication (ask x 100 > ref x 101, bid x 100 < ref x 99); `INSUFFICIENT_BUYING_POWER` and `INSUFFICIENT_POSITION` from model cash and shares; lots hold the price without fees; realised P&L is the sum of (proceeds - basis). After each operation the test compares the outcome code, `CASH`, `FEES`, `POSITION_COST`, `REALIZED_PNL`, per-instrument shares and every open lot with the database.

## 8. Deviations, surprises, spec questions

**Additions the prompt did not list (please confirm):**

1. **Two `SECURITY DEFINER` lock functions (migration 0020).** The prompt requires locking the accounts row and the CASH ledger row, but PostgreSQL needs UPDATE privilege for any row-locking clause, and M1 deliberately withheld UPDATE on `ledger_accounts` (balances move only through entries). `lock_account_for_order(uuid)` and `lock_cash_balance(uuid)` (owner: migrator, fixed `search_path`, EXECUTE revoked from PUBLIC and granted to `vantage_app`) take exactly those two locks and return the account status and the cash balance. The app gains no table privilege. A side effect: the app can take row locks on any account through these functions (a small denial-of-service surface for a compromised app, which can already trade).
2. **Migration 0021 fixes a bug in my own 0018** (the I5 trigger function). Forward-only; 0018 is unchanged.
3. **`reconcileAccount(client, id, { trading: true })`.** The prompt says to extend `reconcileAccount`. The M1 ledger tests post `FILL` ledger transactions with `POSITION_COST` but no lots or orders and expect a clean result, so the trading checks are opt-in. Every account that trades must use `{ trading: true }`. The reverse I6 check (a `FILL` ledger transaction without an execution) is not made, for the same reason.
4. The M1 ledger repository can now record `order_id` and `execution_id` on a ledger transaction (optional fields; there are no foreign keys, so they are known before the order is inserted).
5. A partial unique index `fee_schedules (asset_class, version) WHERE exchange_id IS NULL`: DATABASE section 8's `UNIQUE (asset_class, exchange_id, version)` does not stop two global version-1 rows because NULLs are distinct.

**Spec questions I resolved conservatively:**

6. A SELL whose commission exceeds its proceeds could drive cash negative; the prompt's rule list has only a position check for SELL, so the engine does not add one. The database `CHECK` would abort the transaction (a typed `InsufficientFundsError`, not a rejected order). With the v1 schedule (0 bps) this cannot happen; the rule needs a decision before fees can exceed 100 bps of notional on a SELL.
7. Orders of other statuses (`ACCEPTED`, ...) are not blocked by the I5 trigger. D-49 says M4a inserts only `FILLED` or `REJECTED`; the function only validates `filled_qty`, FILLED and REJECTED.
8. Time-in-force is left at the table default `DAY`; it has no effect for a synchronous market order.
9. The order id used for FIFO ties is the lot's UUIDv7, so two lots opened at the same instant are consumed in creation order within one process. If several API processes ever create lots in the same millisecond, ordering between them is by id, not strictly by creation.

## 9. Known limitations and what M4b needs

- Throughput: 14 orders/s sequential on this machine (about 20 statements per order). If the 200 fills/s target is to be met, the number of round trips per order needs reducing (batching inserts, a single stored function) and a parallel measurement on the reference VM.
- Reconciliation must be called with `{ trading: true }` for trading accounts; the nightly job (later) must also set `FROZEN_RECON`, which needs its own privilege decision.
- Only MARKET orders, whole shares, USD, US stocks and ETFs, synchronous fills; no limit or stop orders, reservations, cancel, partial fills, outbox, FX, crypto or marks. No HTTP endpoints exist; nothing here is reachable from the API yet.
- Unchanged from earlier phases: file mode 0600 is unverified on Windows; CI has never run (nothing pushed); quotes are FIXTURE data; rate limits are in memory; no email verification.
- **M4b needs:** a service that resolves the command (instrument by symbol, the quote and its freshness from `QuoteService`, the fee schedule row, `allowExecutionOnDelayed`, the trading-enabled flag, `now`) and calls `executeMarketOrder` inside one transaction together with the `idempotency_keys` row; mapping rejects, replays and `ClientOrderIdMismatchError` to HTTP responses; an `Idempotency-Key` request-hash comparison; read endpoints for orders, positions and executions (showing the quote, `model_version` and the DELAYED label); and `{ trading: true }` reconciliation in any health or admin check.
- Local state: this checkout's database was reset at the end of the clean-clone run and migrated to 0021 (port 55433).

M4b was not started.
