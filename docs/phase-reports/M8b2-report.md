## 9. Deviations, interpretations and open questions

1. **`stepMultiple` is derived, not a fixed integer per class (D-99). Please confirm or object.** One tick multiple cannot give a comparable span for BTC at 90,000 (tick 0.01) and DOGE at 0.15 (tick 0.00001): a constant that spans 0.15% of BTC spans about 65% of SOL (150, tick 0.01) and would take XRP (0.55, tick 0.0001) bids below zero. So the documented per-class constant is the **span of a 15-level book as a share of the mid**: CRYPTO 15 bps (0.15%), EQUITY and ETF 30 bps (0.30%), and `stepMultiple = max(1, floor((bid + ask) x spanBps / (2 x 10,000 x 14 x tick)))`. It does not depend on the requested level count (a 7-level book is a prefix of a 25-level book). Numbers: BTC at 89,990.00 / 90,010.00 gives 964 (step 9.64; the 15-level span is 0.1499% of the mid); AAPL at 189.95 / 190.00 gives 4 (step 0.04; 0.295%). It is a single function (`depthStepMultiple`) if you prefer a fixed constant.
2. **Size shape (D-99).** Notional per level = base x shape x noise: base USD 30,000 (crypto) and 40,000 (stocks, ETFs). Stocks: shape 8,000 / (level + 3) permille (2,000 at the top down to 444 at level 15), noise 0.5 to 1.5. Crypto: shape 1,500 x 0.94^(level-1) permille (1,500 down to about 630), noise 0.2 to 2.0. Size = notional / price rounded down to the step, at least max(min_qty, step). The hash is the SIM feed's `hash4` keyed by (seed, symbol, 5-second quote bucket, side x 64 + level).
3. **Cache key includes the bid and ask**, not only (symbol, bucket, levels) (D-101): within one 5-second bucket the quote can change, and the best bid and ask must always equal the current quote. Freshness and `quoteAt` are computed on every request, never cached.
4. **my-orders is a separate route**, not an `include=` option (documented in `docs/api.md`). Its `levels` query should equal the one the book uses. A BUY is placed on the bid ladder and a SELL on the ask ladder; any other order, or any order when there is no ladder, is `onBook: false`.
5. **Rate limit:** cost 1 up to 15 levels, 2 above; allowance `DEPTH_RATE_LIMIT_PER_MINUTE` (default 120) per client address on the public route and per user on my-orders. The public route is keyed by the resolved client address (trusted-proxy rule): behind the web proxy without `TRUSTED_PROXY_CIDRS` all web users share one address and one allowance, as for login. A 5-second poll with 15 levels uses 12 points a minute per tab.
6. **Response extras (allowed by the prompt):** `spread`, `mid` (exact strings from the server) and `cumPct` per level (integer percent of the larger side's total) were added to the depth response; they are in the contract and documented.
7. **Verification ran in the main checkout, not in a fresh clone**, as you allowed ("use the clean clone only for the final verification run if you want"). The tree was clean at `b520874` apart from the e2e-regenerated screenshots. I did not re-verify in a fresh clone.
8. **Port.** The main checkout's `.env` and `.env.infra` are now on 56433 (untracked). The old clone `C:\dev\vantage_m8b1_clean` also uses 56433; both use the one container name `vantage-postgres-1`, so do not run both at once.
9. `pnpm db:down` was run at the end, so the dev database is stopped (data is kept in its volume; `pnpm db:up` restarts it).

## 10. Known limitations and what M9 needs

- **The book is a display only.** Nothing fills against it, its sizes are not liquidity, and it has no depth history or streaming (polling only, 5 s like the quote). Bars are cumulative within a side, relative to the larger side.
- **The book only offers REAL_TIME and DELAYED quotes.** In the default NYSE profile a stock's book is therefore absent outside the session ("Depth unavailable: market is closed."); the always-open profile and crypto show books around the clock.
- **Clicking a price** only works when the ticket is already in Limit mode; it does not switch the mode (by design, M9 may want a "use as limit" that switches).
- **Typed-before-ready quantity input (M8b-1 F5): NOT investigated in this phase.** The order ticket changes of this phase (three optional props and three effects) did not touch the quantity field, and the existing fractional-crypto keyboard test passed in the one full e2e run of this phase (105 passed), but a single pass is not proof. M9, which will rebuild the instrument page around the terminal, should verify that a quantity typed right after navigation is kept (read the field value on mount), under load.
- **M9 needs from this phase:** `DepthBook` takes `state`, `canPick`, `onPick` and has no layout assumptions beyond a column of about 360 px and up; `useDepthPoll(symbol, pollMs)` returns a stable `refreshNow`; the ticket exposes `onKindChange`, `pricePick` and `onSettled`. The server provides `spread`, `mid` and `cumPct`, so a new layout needs no arithmetic. Depth for the order-entry panel should keep the honesty sentence adjacent to the book.
- Machine reliability: Windows suspended the machine during two of my runs (F1, F3) despite a keep-awake request. A run whose duration is hours is a sleep.
