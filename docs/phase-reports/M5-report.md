### Performance (`pnpm bench:portfolio`: one account, 200 open positions, 5,000 executions; real HTTP in-process, Windows + Docker Desktop, noisy machine)

| Request                                      | p50     | p95      | max      | DB round trips per request |
| -------------------------------------------- | ------- | -------- | -------- | -------------------------- |
| `GET /v1/portfolio` (200 positions), 30 runs | 93.4 ms | 162.2 ms | 174.0 ms | 5.0                        |
| `GET /v1/executions?limit=100`, 30 runs      | 48.7 ms | 91.8 ms  | 111.0 ms | 2.0                        |
| `GET /v1/ledger/activity?limit=100`, 30 runs | 32.3 ms | 77.6 ms  | 85.0 ms  | 2.0                        |
| walk of all executions, 50 pages of 100      | 38.9 ms | 82.0 ms  | 103.0 ms | 2.0 per page               |

No N+1: the portfolio costs 5 round trips (session, BEGIN, balances, positions with lot cost, COMMIT) whatever the number of positions; the earlier run with 100 positions also took 5. The realised P&L of each SELL is a single indexed correlated lookup (`lot_closures(close_execution_id)`, added in migration 0023). The portfolio's remaining time is mostly building and validating 200 position objects (zod) and 200 in-memory quote and freshness lookups. A first (flawed-seed) run with 100 positions gave p50 51.6 ms; these two runs were not taken under equal machine load, so I draw no scaling conclusion from them.

## 8. Deviations and spec questions

- **PRD section 5.6 asks for an equity-curve snapshot at least hourly while markets are open;** D-62 (approved) says daily after the NYSE close. I followed D-62 and recorded the gap in the decision's consequences. Hourly snapshots can be a later job with the same table.
- **"Stored marks" has no table behind it.** No marks or daily-candle table exists (M3b). I interpreted it as the quote store's last accepted quote, valid for a day only if its provider timestamp is on that exchange-local date and not after the close. Catch-up days therefore are usually incomplete; the report and `docs/portfolio.md` say so. If you meant something else (for example persisting closes at write time), please say.
- **Cash and quantities for a snapshot day are rebuilt from stored `executions`** up to the close (the only dated stored data), not from `ledger_transactions.created_at`, because ledger timestamps are database time while executions carry the application clock. They agree today (a test compares the snapshot with the portfolio at the same instant).
- **"No snapshot before the account existed"** uses `accounts.created_at` (database time). Tests set it explicitly.
- **First-run rule:** an account with no snapshot gets only the latest closed session, never a backfill from before the job first ran; each later run writes every missed session (at most 366 per account per run).
- **Money format:** amounts are 2 dp HALF_EVEN strings with an `exact` companion; prices (`avgCost`, `mark`, `price`) are canonical and unrounded. I added `exact` objects to every money-bearing response rather than "where useful".
- **Reserved cash:** equity here is `cash + valued positions` (D-61). `RESERVED` is always 0 until limit orders exist; when it is not, equity must include it (TRADING_ENGINE section 3).
- **Extra filters and fields not in the prompt:** `symbol` filter on `/v1/executions`; `title` (plain-language label) on activity items; `generatedAt` on the portfolio.
- **No read rate limit** was added (ARCHITECTURE section 6 mentions 300 reads per user per minute); the M2 in-memory limiter is not wired to the read routes.
- **Refactor of M4b code:** the cursor helper moved to `common/cursor.ts` and the orders service uses it; the orders tests pass unchanged. The M4a reference model moved to `testing/reference-model.ts`; its tests pass unchanged.

## 9. Known limitations and what M6 needs

Limitations:

- The quote store is in memory, one last quote per symbol; after a restart every position is UNAVAILABLE until quotes arrive (shown honestly, not zero-valued). Snapshot marks have the limitation described above.
- The snapshot job runs inside the API process, one tick a minute, and does not start when `APP_ENV=test`; with several API processes each runs it (safe, the insert is idempotent).
- Calendars: the snapshot day is the NYSE day for every account (all instruments are US today).
- No day change or benchmark comparison (needs prior-close data); no allocation breakdown; no FX or INR; no cancelled, open or partially filled orders exist yet.
- Portfolio p95 at 200 positions is about 160 ms on this machine; if it matters, cache the per-exchange calendar state per request and avoid zod re-validation of the response.

Endpoints the UI can use (all JSON, session cookie, CSRF `Origin` header on POST; the account is always the session user's; full detail in `docs/api.md`):

- Auth and profile: `POST /v1/auth/register`, `POST /v1/auth/login`, `POST /v1/auth/logout`, `GET /v1/me`, `GET /v1/account` (cash, equity, initial capital).
- Market data: `GET /v1/instruments/search?q=`, `GET /v1/instruments/:symbol`, `GET /v1/quotes?symbols=` (labelled `source` and `freshness`), `GET /v1/market/status`.
- Watchlists: `GET/POST /v1/watchlists`, `PATCH/DELETE /v1/watchlists/:id`, `POST /v1/watchlists/:id/items`, `PUT /v1/watchlists/:id/items/order`, `DELETE /v1/watchlists/:id/items/:symbol`.
- Trading: `POST /v1/orders` (header `Idempotency-Key` required), `GET /v1/orders`, `GET /v1/orders/:id`, `GET /v1/positions`.
- Portfolio (new): `GET /v1/portfolio`, `GET /v1/portfolio/history?from&to`, `GET /v1/executions`, `GET /v1/ledger/activity`.
- Health: `GET /health`, `GET /health/ready`.

M6 should: show `freshness`, `markBasis`, `quote.asOf` and the `incomplete` flag wherever a value is shown (never present an UNAVAILABLE position as a number); use the 2 dp strings for display and `exact` only for calculations; show `totalReturn: null` as "not available" rather than 0; use the `Idempotency-Key` on order submit and reuse it on retry; handle 429 (`Retry-After`) and `REJECTED` orders (a 201 with `rejectCode`); and draw the equity curve from `/v1/portfolio/history`, marking `valuedComplete: false` points. Still missing for a full app: real-time updates (outbox and WebSocket), limit and stop orders with cancel, a real market-data provider (M3b), daily candles and prior closes for day change, hourly snapshots, email verification and password reset.
