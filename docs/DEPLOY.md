# Deploying VANTAGE (research and checklist; nothing here was deployed)

This document was written in M10 as **research only**. No account was created, nothing was deployed, and no token or secret was requested or used. Everything about hosting providers was checked on **2026-11-22** and can change; each uncertainty is marked **UNVERIFIED**.

What you are deploying: three processes (the web app, the API, PostgreSQL 16) plus a one-shot migration step. The container images and a working compose stack are described in [DOCKER.md](DOCKER.md). The simulated market (`MARKET_DATA_SOURCE=SIM`) is the only data source the app can run in staging or production: `FIXTURE` is refused there and `PROVIDER` has no adapter (see the rules in section 1).

## 1. Environment variables

Two validated schemas exist: the API's (`packages/config/src/index.ts`) and the web app's (`apps/web/src/lib/config.ts`). "Required in production" means required when `APP_ENV` is `production` (or `staging`, which behaves the same). A wrong or missing value stops the process at start with the variable **names** (never the values) and exit code 2.

Rules the schemas enforce, so a wrong setup fails at start instead of running unsafely:

- Staging and production refuse `FIXTURE` data, require `DEMO_MODE=true` with `SIM`, require `TRADING_ENABLED`, `TRUSTED_PROXY_CIDRS`, and (web) `API_BASE_URL` and `TRUST_FORWARDED_FOR`, and refuse `COOKIE_SECURE=false`.
- An application process that holds `DATABASE_MIGRATOR_URL`, `POSTGRES_SUPERUSER_PASSWORD` or any `VANTAGE_*_PASSWORD`, or whose database user is `postgres` or `vantage_migrator`, refuses to start (the config guard in `packages/config`).
- The browser only talks to the web app. The web app forwards `/api/*` to the API, so the cookie belongs to the web origin and there is no cross-origin traffic.

**Caveat on `TRUSTED_PROXY_CIDRS` (UNVERIFIED on every platform below).** The API's per-address rate limits (login, registration) key on the client address. With `none`, every visitor appears to come from the web service's address and shares one limit bucket, so one visitor can lock out the others. To get real client addresses, the web app must forward `X-Forwarded-For` and the API must trust the web service's address range. I could not verify which address range a given host presents; find it on the first deployment (the API logs the address it sees) before relying on per-address limits.

## 2. Database setup

- **Roles:** `vantage_migrator` owns the schema and runs migrations; `vantage_app` is what the API uses and has no UPDATE on `accounts` or `ledger_accounts` (two narrow `SECURITY DEFINER` functions take the row locks instead). `infra/postgres/01-bootstrap.sh` creates both roles and the database `vantage_dev` on an empty volume. On a managed Postgres you create the same two roles and the database by hand with equivalent grants (read the script; it is short). **UNVERIFIED on every managed host below.**
- **Extensions:** migration 0001 runs `CREATE EXTENSION IF NOT EXISTS citext` and `pg_trgm`. The role running migrations must be allowed to create them (**UNVERIFIED** on each host; both are common and ship with PostgreSQL's contrib).
- **Migrations:** plain SQL files in `db/migrations`, **forward-only**: there is no down step and an applied file is never edited. Run them with the `migrate` target of the Dockerfile (a one-shot job that exits 0 when done) or `pnpm db:migrate`. Running it twice is a no-op.
- **Connections:** use a **direct** (not pooled, not transaction-mode) connection string. The matcher takes a session-level Postgres advisory lock and the order path takes row locks inside transactions; a transaction-mode pooler can break the first. **UNVERIFIED** against any host's pooler.
- **Backup and restore:** the ledger is the record of truth, so back up the whole database. `pg_dump` (custom format) and `pg_restore` into an empty database are enough for a demo; restore, then run the migration step (a no-op) and the reconcile check. The reconcile code is `apps/api/src/modules/ledger/reconcile.ts`. A managed host's point-in-time recovery is a paid feature on most free plans.

## 3. Reverse proxy requirements

- **HTTPS is required** (the session cookie is `Secure`). Terminate TLS at the platform; the web service itself speaks plain HTTP.
- Forward `X-Forwarded-For` (client address) and `Host`; set `TRUST_FORWARDED_FOR=true` on the web app only if the proxy really appends the client address.
- **WebSockets are not needed:** the app polls over plain HTTP.
- Request bodies are small JSON (orders and forms); a 1 MB limit is plenty. No uploads.
- The API does not need a public address when the platform offers a private network; if it is public, `WEB_ORIGIN` and the session cookie still gate state-changing requests, but a smaller surface is better.

## 3b. Health checks

Web: `GET /login` (the container health check uses it; `/api/health` through the proxy reaches the API). API: `GET /health`. Both are used by the compose stack and need no credentials.

## 4. Operational limits (documented, not fixed)

- **Run exactly one API instance.** Rate limiters and quote caches are in process memory, so two instances would each have their own limits and caches. The matcher takes a Postgres advisory lock, so an accidental second instance only skips its ticks; correctness does not depend on it.
- **Demo accounts accumulate.** The ledger is append-only, so a demo account and its entries are never deleted. Every press of "Try the demo" adds permanent rows. The registration and login rate limits are the only brake; switch `DEMO_ACCOUNTS` off to stop it.
- **Sleeping hosts pause the world.** If the API sleeps (free tiers), the simulated feed and the matcher stop. Prices are a deterministic function of the seed and time, so they resume correctly, but a resting limit order fills only while the API is awake and a quote is evaluated.
- **Clock changes** (a machine sleeping) matter only to the tests; the app uses the database and process clocks.
- **Graceful stop:** the API logs `shutting down`, closes its pool and exits 0; the web container exits 143 on SIGTERM (Node's default; it holds no state).
- **Data loss on free databases:** some free databases expire (see the table). A demo that is shown to interviewers must not be on a database that disappears.

### What I could not verify

- Render's region list (is Singapore available for free services?) and whether free services can use a private network to reach each other.
- Whether Render can build a **specific stage** of a multi-stage Dockerfile (the repository has `api`, `web` and `migrate` targets). If not, a small per-target Dockerfile or a build argument is needed.
- Whether any host's Postgres lets the migration role create `citext` and `pg_trgm`, and create the two roles.
- What the "5h" free Koyeb database allowance means, and whether Koyeb has any free web service.
- Railway's Singapore region on the Hobby plan, and what the Free plan does when its credit runs out.
- Real network latency from India to any region (nothing was measured).

### Recommendation

**Primary: Render for the two web services, Neon (Singapore) for the database.** It is the only combination I found where every piece has a free tier that is documented, and it avoids the worst trap of the single-vendor route: Render's own free Postgres is **deleted 30 days after creation**, which would destroy a demo that is shown over weeks. Neon's data persists while idle. The costs are honest ones: the free Render web services **sleep after 15 minutes and take about a minute to wake** (so the first interviewer click is slow, and resting limit orders fill only while the API is awake), Singapore for the web tier is unconfirmed, and the Neon connection must be the direct one (section 2).

**Fallback: Railway Hobby ($5 per month).** It keeps all three pieces in one project and bills by usage; I did not confirm that services never sleep (UNVERIFIED), which matters for the matcher and the feed. It costs money (small), and its Singapore region and Docker-target behaviour are unconfirmed.

Not recommended for this: Fly.io (no free tier for new accounts) and Oracle Always Free (the allowance was reported cut, capacity is scarce in Mumbai, and you would run and patch the server yourself).

### Steps the founder would do in the host's dashboard (no token and no secret in chat or on a command line)

Do these yourself in a browser. Never paste a password, a connection string or a token into chat, an issue, a terminal command or a commit.

1. **Neon:** sign up in the browser, create a project in **Singapore** (the region cannot be changed afterwards). In the project's SQL editor, create the two roles and the database objects as `infra/postgres/01-bootstrap.sh` does, choosing the passwords in the editor (long random strings from a password manager). Note the **direct** (non-pooled) connection details inside the Neon dashboard only.
2. **Render, migration step:** create a one-off or pre-deploy job from this repository's `migrate` target (a public repository needs no access grant; a private one needs the platform's own repository connection). In the job's **Environment** page add `DATABASE_MIGRATOR_URL` by typing or pasting the value **into that field** (it is stored as a secret). Run it once and check it exits 0. Delete the variable from any service that is not the job.
3. **Render, API service:** a Docker web service from the `api` target, **one instance**. Environment page: set the variables from section 1 (`APP_ENV=production`, `MARKET_DATA_SOURCE=SIM`, `DEMO_MODE=true`, `SIM_SESSION=ALWAYS_OPEN`, `CRYPTO_FEED=sim`, `MATCHER=on`, `TRADING_ENABLED=true`, `COOKIE_SECURE=true`, `LISTEN_HOST=0.0.0.0`, `PORT` as the platform requires, `WEB_ORIGIN` as the web service's https URL, `TRUSTED_PROXY_CIDRS` as decided in the caveat) and `DATABASE_URL` typed into its field. Use the health check path `/health`.
4. **Render, web service:** a Docker web service from the `web` target. Environment page: `APP_ENV=production`, `API_BASE_URL` as the API's address, `TRUST_FORWARDED_FOR`, `DEMO_ACCOUNTS=on` (only for the public demo). Health check path `/login`.
5. **Order:** run the migration job, start the API, then the web service. Open the web URL, press "Try the demo", place a market order, then read the API log for the client address it saw and fix `TRUSTED_PROXY_CIDRS` if needed.
6. **Domain (optional):** add the custom domain in the web service's settings and create the DNS record the dashboard shows at your registrar. Update `WEB_ORIGIN` on the API to the new origin and redeploy.
7. **Before showing it:** wake both services once (open the page and wait a minute) so the first view is not cold; test on a real phone with the checklist in the M9b report.
